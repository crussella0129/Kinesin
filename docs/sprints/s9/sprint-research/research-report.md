## 1. Sprint Goal
Reach an **operator-approved, local (stdio) MCP tool server** and expose its
discovered tools to the model through the *same* authority, allow-list, byte, and
timeout gates the eight compiled tools already pass. The operator declares each
server (a trusted binary, like the model endpoint) and allow-lists which of its
tools a run may call; discovery and the server's own schema never establish
authority; the server's tool **descriptions and results are untrusted data**,
exactly as file contents are; MCP tool calls mint no evidence (like
`run_command`). Replay must stay pure: the discovered tool set is **frozen into
the run config** at capture (as `ModelConfig`/`cache_prompt` already are) and
replay re-validates the recorded call + observation against that frozen set
without reconnecting. Remote transport, OAuth, and credential delegation are
explicitly out of this sprint (→ INT-0020). This is an architecturally invasive
sprint: it generalizes the closed `ToolName` enum into a tool *reference* that
both a compiled tool and an MCP tool satisfy, touching config, model, runner, and
replay.

## 3. External Sources
- [rmcp — official Rust MCP SDK](https://github.com/modelcontextprotocol/rust-sdk) ([docs.rs](https://docs.rs/rmcp/latest/rmcp/), [crate](https://crates.io/crates/rmcp)) — **v3.3.0 (2026-09-10)**, tokio-based, the official SDK. Client MVP: features `client` + `transport-child-process`; `let client = ().serve(TokioChildProcess::new(Command::new(...))?).await?;` performs `initialize`; then `client.list_all_tools()` (→ `Tool { name, description, input_schema }`) and `client.call_tool(CallToolRequestParam{ name, arguments })` (→ `CallToolResult { content, is_error }`). Pluggable `Transport` trait; HTTP client transport (`transport-streamable-http-client-*`) is the seam INT-0020 will use.
- [MCP specification 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18) — tools lifecycle (`initialize` → `tools/list` → `tools/call`), structured tool output, and the **security section**: MCP servers are classified as OAuth resource servers; clients MUST implement RFC 8707 resource indicators to stop a malicious server obtaining a token minted for another; SSE-over-HTTP deprecated. The auth material is INT-0020's basis; the tool lifecycle is INT-0005's.
- [NSA — Model Context Protocol Security CSI (2026)](https://www.nsa.gov/Portals/75/documents/Cybersecurity/CSI_MCP_SECURITY.pdf) — directly on the project's "NSA-grade" bar: approve/allow-list servers, treat tool descriptions **and** outputs as untrusted (tool-poisoning + prompt-injection via results), least privilege per tool, isolate/sandbox servers, and prevent token passthrough / confused-deputy. Maps 1:1 onto the trust boundary this sprint implements.
- [Microsoft MCP security best practices (2025)](https://github.com/microsoft/mcp-for-beginners/blob/main/02-Security/mcp-security-best-practices-2025.md) + the MCP security framing carried from the [sprint 5 survey](../../s5/sprint-research/research-report.md#3-external-sources) — prompt injection, tool poisoning, session hijacking, confused deputy, token passthrough. Confirms the residual-risk list.

## 4. Risks, Unknowns, Dependencies
- **Risk (architectural scope creep):** the closed `ToolName` enum is assumed in config/model/runner/replay/policy. Generalizing it is invasive and could regress the compiled-tool path or replay purity. Mitigation: introduce a `ToolRef` (compiled `ToolName` ∪ `Mcp{server,tool}`) that keeps `Hash`/`Eq`/serde and a conservative `is_mutating()` (MCP = mutating by default, so it stays barred from checked runs); keep compiled dispatch byte-for-byte unchanged; add MCP as a *sibling* branch, not a new `execute` arm. All existing tests must stay green.
- **Risk (replay non-determinism):** a server could advertise different tools/schemas on different connects. Mitigation: **freeze** the discovered `{name, description, inputSchema}` set into the run config at capture (the `cache_prompt`/`ModelConfig` precedent); replay validates against the frozen set and never reconnects; a live re-discovery that disagrees surfaces as a fingerprint divergence, not a silent accept.
- **Risk (tool poisoning):** server-supplied tool **descriptions** are injected into the model prompt and can attempt manipulation; results can carry injected instructions. Mitigation (and the intent's core): descriptions/results are **data** — they cannot grant a tool or install policy (policy is operator config); effects stay bounded by the allow-list + byte/time gates regardless of description text; the threat-model (INT-0015) prompt-injection-as-data posture already covers this and a red-team test asserts it.
- **Unknown (sandbox interaction):** INT-0012's mandatory Linux sandbox confines argv the **model** proposes via `run_command` (untrusted origin). An MCP server is a binary the **operator** declares (trusted origin, like the llama endpoint) and may legitimately need network (e.g. a fetch server), which the seccomp denylist blocks. Decision for the MVP: the MCP **server process** is operator-trusted and **not** force-sandboxed; confining a not-fully-trusted server (per-server network/FS policy, possibly reusing INT-0012) is named as a follow-up. The roadmap's "Executes under the INT-0012 sandbox" note is clarified accordingly.
- **Dependency:** none blocking. Builds on the existing tool/authority/replay machinery. **INT-0020** (remote transport + delegated auth) depends on this core and on the transport-privacy boundary (INT-0008/0009); **INT-0015** owns the residual prompt-injection/token-passthrough documentation. No new CI job needed (rmcp is a normal dep; `cargo deny`/`audit` will vet its subtree — a licence/advisory surprise there is the one supply-chain risk to check at build).

## 5. Recommended Approach
**Primary — a local stdio MCP client behind a generalized tool reference, one operator gate, frozen-for-replay.**
1. **Config / trust boundary:** add `[[mcp.servers]]` (operator-declared: `name`, `command` argv, optional per-server exposed-tool list). Generalize the run allow-list to a `ToolRef` so `workspace.tools` and the per-owner narrowing carry both compiled names and `mcp__<server>__<tool>` identities (adopt the `mcp__server__tool` namespacing to avoid collisions with the 8 compiled names). Two gates: the server must be operator-declared **and** the specific tool must be in the run's allow-list.
2. **Discovery + freeze:** at run start, spawn each declared server (`rmcp` `TokioChildProcess`), `initialize` + `list_all_tools`, capture `{name, description, inputSchema}` for allow-listed tools, and **freeze** it into the run config (replay reads the frozen set; never reconnects).
3. **Model seam:** `runner::options` appends namespaced MCP names to `ModelOptions.tools`; the model.rs compiler emits the **discovered** `inputSchema` for an MCP name (from the frozen map) instead of the closed `match`.
4. **Dispatch:** in the runner ladder, an MCP name routes to a `tools/call` sibling path — args validated against the frozen `inputSchema` (not `TypedToolArgs`), the same `resources.tools` permit + `deadline` + byte cap applied, the result recorded as an **untrusted** observation that **mints no evidence**. Denial ladder mirrors compiled tools (unknown server/tool, not-approved, invalid args).
5. **Replay:** the frozen schema set + recorded observation make the MCP branch replay exactly like a file read; generalize the name-map + arg-validity check to `ToolRef` + `inputSchema`.
6. **Tests:** an approved MCP call succeeds and is bounded; an unapproved server / un-allow-listed tool is denied; server-supplied description/result text is treated as data (cannot grant a tool or alter policy); replay of an MCP run reproduces without reconnecting. Use a tiny in-repo stdio echo/fixture MCP server (a `src/bin` fixture, like `cmd-fixture`) so tests need no external `npx`/network.

**Alternative considered — a bespoke JSON-RPC-over-stdio client (no rmcp).** Rejected: re-implements the protocol/lifecycle the official SDK already tracks to the 2025-06/2026-07 spec, and adds unaudited surface; rmcp is the official, `cargo deny`-vettable SDK. **Also considered — remote/HTTP MCP in this sprint.** Rejected/split: OAuth resource-server auth + RFC 8707 + confused-deputy defense is a whole delegated-authorization problem that dwarfs the stdio core; it becomes **INT-0020** so INT-0005 can be honestly *realized* in one sprint.

**Rationale:** the stdio, operator-approved core is the smallest change that delivers the SotA capability (an external tool ecosystem) while preserving Kinesin's invariants — capability scoping, deterministic replay, untrusted-content-as-data, and the checked-run bar. Splitting remote/auth keeps each sprint's "realized" claim honest, matching the INT-0013 (release-artifacts → parking-lot) and INT-0012 (Windows → INT-0019) precedent.
