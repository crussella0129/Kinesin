# Sprint 16: explanation is not execution

## Observations that constrain a fix

The [frozen diagnostic sequence](../sprint-tests/diagnostics/attempt-ledger.md)
changed the initial observation while preserving task, model, source, protocol,
grants and limits. No assistance, actual root filenames, and complete unmodified
source each produced two answer objects and no tool operation. Available source
changed what the model could describe, but did not produce applied work.

The wire explicitly instructed real actions, read-before-edit, honest claims and
actual preview URLs, and offered list/read/edit/write/preview schemas. The model
chose a valid `answer` branch rather than submitting a malformed action. There
was no tool worker or preview failure to repair: none was invoked. It stopped
well before time, output, tool and model-turn ceilings. Larger budgets or a tool
executor fix have no demonstrated connection to these three failures.

C's first response correctly points to resetting `totalCents` to the latest
price. Its proposed deletion is itself insufficient; the second answer claims
the accumulator change. Both claim work without a tool event or changed byte.
This supports partial source comprehension, not verified reasoning or repair
competence. It falsifies the narrow prediction that source access alone would
be sufficient on this sample under the existing action interface.

## Deeper boundaries

1. **Selecting an action remains a model decision.** A syntactically valid
   answer satisfies the output grammar even when requested work is absent.
   Ordered serialization solved two explicit-file diagnostics in S15, so the
   entire executor is not universally incapable of effects. But a working
   action encoding does not ensure that behavioral app requests select it.
   Instruction load, task framing, model/interface fit and answer-branch bias
   remain hypotheses; these three runs do not isolate them.
2. **The completion reviewer is the same generative component.** Existing
   `completion_review` appends truthful operation context once and accepts the
   next answer. Here the empty operation record produced another answer rather
   than action. This cannot serve as independent proof of work. The core's
   `unchecked` receipt is accurate; the candidate's completion claim is not.
   Any future user-facing account must keep these two sources visibly distinct.
3. **Observation and execution have different prerequisites.** Automatically
   supplying more files would add authority, privacy, accounting and replay
   complexity without a demonstrated execution benefit here. Root listing is
   therefore not implemented. Complete source was supplied only as frozen
   diagnostic data, not as a product retrieval feature.
4. **Progress needs task behavior, not stage counts.** No tool calls means no
   applied progress in this case; tool calls alone would still not prove a
   correct cart. Existing receipts and bounded facts can identify contradictions
   and retain partial work, but do not by themselves supply semantic acceptance.
   Reintroducing rigid read/write/run milestones would repeat a rejected proxy.

## Next research obligation, not execution authorization

Before another context subsystem or workflow graph, inspect how the model sees
the action-versus-answer choice and whether task-shaped instructions overload
or bias it. A future narrowly approved contrast should keep this repair seed,
profile and observation fixed, change one action-interface/instruction variable,
and require actual effects plus browser behavior and a distinct held-out repair.
Include an ordinary no-effect question as a design control so forcing tool-only
output cannot masquerade as progress. Bound new calls explicitly and preserve
all failures; no additional submission is authorized by this document.

Separately investigate a truthful final presentation driven by machine-owned
effect facts: expose zero operations and unverified behavior next to claims.
That could reduce false assurances but must be scored as reporting improvement,
not app-delivery success. Do not parse model prose into authoritative effects or
infer task completion from a generic activity threshold.

The same seven-billion-parameter profile may be a poor fit for this interaction,
but no model comparison was performed here. No unique root cause, reliable
repair ability, productivity gain or proof that observations never help follows
from this bounded negative sequence. Full usefulness remains the unchanged
storefront plus same-session follow-up with zero operator corrections.
